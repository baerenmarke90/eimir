# Internationalization and localization

As of: 2026-11-06. Owning delivery: [#1664](https://github.com/baerenmarke90/eimir/issues/1664).

## Supported product languages

German (`de`) and English (`en`) ship with the application. German is the final
fallback. Language availability and personal selection are **Non-paywallable**
under the Accessibility essentials & i18n localization matrix row, identically
in Cloud and Self-Hosted. Existing feature entitlements still apply.

`web/src/i18n/resources.ts` is the Web registry. Each entry declares a language
name in that language, writing direction and a complete resource pack. German
retains its existing domain fragments; English is a complete keyed JSON pack.
Feature components use stable domain keys, never German source text as a key.
The Settings options, supported languages and document direction derive from
this registry. Additional languages do not require feature-specific branches.

## Detection, personal ownership and persistence

Before sign-in, resolve the **complete ordered** browser/device language list,
normalizing supported regional/script variants (for example `de-CH`, `en-US`)
and progressively matching supported tags. If none matches, use German.

Settings → Appearance contains one personal native select: Automatic (device
language), Deutsch and English. Each Account owns its own mode and monotonically
increasing language version. An explicit supported language wins over the device.
Automatic uses the current device list. The same resolver handles live OS/browser
`languagechange` events without replacing the route or its mounted editor.

`GET/PUT /api/v1/account/language-preference` uses the authenticated Account,
`If-Match` and `ETag`; it accepts no target Account, Space or time zone. Concurrent
writes serialize on that Account, and a stale version returns the existing
machine-readable conflict contract. Settings retains the attempted choice and
offers a deliberate reload/retry. An offline save fails immediately and is never
queued for reconnect.

The existing sign-in and `/auth/me` Account metadata includes mode, effective
locale and language version. Startup therefore requires **no additional read**.
The client subscribes to the same Account-scoped query as Settings. Automatic
mode reports a changed effective device language through the versioned write;
a late response cannot change a replacement Account. On conflict it reads the
current authoritative preference rather than overwriting it blindly.

Only the currently signed-in session snapshot with an unexpired refresh
credential can supply an initial explicit override. Web keeps this in its existing tab-scoped session storage; Android
uses the existing instance-bound encrypted native session slot. No new plaintext
persistent preference or translation cache is introduced. Logout clears the
Account scope and resumes device detection. A late `/auth/me` or session write
cannot replace a newer language version for the same Account.

Offline reading retains the confirmed session preference. Unsupported or removed
explicit locales safely use German. Migration `0112` adds Automatic/version zero
without rewriting existing locale, time zone, birthdays or authored content.
The effective Account locale remains the existing background-delivery input.
Full instance backup/restore includes the new Account fields. The existing
relationship Transfer Bundle carries effective locale metadata; importing shared
relationship content does not replace the receiving Accounts' personal mode.

## Text and formatting conventions

- Translate visible copy, accessible names, placeholders, validation, empty,
  loading, error, offline and success feedback through stable keys.
- Use i18next plural suffixes and `Intl.PluralRules` categories. Never implement
  a language's grammar with `count === 1` branches in a component. Preserve
  interpolation placeholders; translate surrounding grammar.
- Use `Intl` with `resolvedLocale()` for displayed dates, relative labels,
  numbers, units and currency. Formatting never changes a stored money amount,
  domain date, Account time zone, reminder, reveal rule or shared calendar day.
- Language changes update document `lang`, `dir`, title/description and React
  translations in place. Do not key a router/editor by language, reload the
  document, reset a draft or clear unrelated authorized product/media caches.
- User-authored titles, notes, answers, comments and names remain unchanged.
  No content is sent to a translation service.
- API errors retain stable `ProblemDetails.code` semantics and English internal
  diagnostics. Client presentation uses existing localized error primitives,
  never raw server diagnostic text as required product copy.

All packs are bundled synchronously. They need no provider, remote loader,
subscription, credentials or startup translation requests. The service worker
also precaches the generated static offline-page language script. Regenerate it
with `npm --prefix web run i18n:generate`; builds/tests check it for drift.

## Recipient delivery and native boundaries

Backend templates live in `backend/src/eimir/i18n/locales/<tag>.json` and are
registered by resource discovery. Delivery uses the **recipient's current**
explicit preference, otherwise their last confirmed automatic locale, otherwise
German. A queued notification email resolves this at dispatch, independently of
the actor and without adding authored content to the generic message.

Magic-link, signup, address verification and password-recovery mail use the same
catalog and resolver. Before an Account exists, bounded HTTP `Accept-Language`
negotiation selects supported signup-mail copy. Mail requests explicitly send
the visible UI locale while preserving their existing headers, so native HTTP
adapters do not depend on browser-added language headers. Known recipients use their saved
personal preference. Status/body anti-enumeration responses and token semantics
remain unchanged. No new query is added to normal signed-in client startup.

FCM and UnifiedPush negotiate `localeVersion: 1` independently of the existing
preview/reference capabilities. New endpoints receive a bounded canonical
recipient locale beside their existing wake/activation or encrypted preview.
Old registrations retain the exact old wire format and device-language
presentation when no recipient-locale metadata is present. Locale metadata cannot
select a different activation, Account, notification target or preview key, and
adds no unencrypted authored content. Changing capability metadata keeps the
existing registration identity.

The Capacitor product uses the Web pack. Native notification templates remain
Android resources (`values` English, `values-de` German); `RecipientLanguage`
selects a configuration context for the recipient without changing the device.
A `product_locale` marker distinguishes an actual native pack from library
fallbacks; an unsupported/malformed tag uses German. Wrapper recovery dialogs
continue to use the OS resource configuration. No separate native product UI or
translation engine is introduced.

## Editorial, provider and legal content

Question/activity UI copy belongs to the existing keyed resources. Proposed
bilingual assignments under #1553 remain with that catalog's owner: this change
does not create a competing catalog or duplicate assignments.

Quotes retain their stable ID, exact quotation, source, provenance and licensing.
Existing quote-language selection and curated fallback pools remain authoritative;
category/source UI labels are translated separately. A different-language quote
is explicitly labeled as its original language and carries that `lang`; it is
never silently translated. Existing saved/local-AI Recap prose likewise retains
its generation locale and content. Recap fallback UI is localized; the reader
labels a different original language rather than regenerating shared prose when
one partner changes a personal preference.

Canonical legal documents, version identifiers and acceptance records belong to
the legal delivery contract (#1657/#1658). UI localization is not an accepted
legal translation. A future unavailable legal translation must explicitly name
the canonical document language; never substitute automatic or unlabeled English
for an accepted German document. At this implementation's baseline, #1658 is a
separate unmerged legal slice and introduces no runtime acceptance UI here.

## Adding a further locale

1. Add a **complete** Web pack with the same semantic keys and interpolation
   variables as German. Supply all cardinal categories required by
   `Intl.PluralRules(newTag)`, including the existing `_other` fallback. Review
   grammar, long text, accessible labels and editorial terminology.
2. Add one `localeRegistry` entry with the canonical BCP-47 tag, native language
   name, `ltr`/`rtl` direction and pack. Automatic detection, the chooser and
   document language/direction then include it without component changes.
3. Add the complete backend recipient JSON catalog with the same tag. Existing
   discovery/negotiation requires no delivery branches. Do not translate server
   diagnostic codes or add another preference column/endpoint per language.
4. Add the corresponding Android resource pack and its canonical
   `product_locale` marker. Android qualifiers may differ from BCP-47 spelling;
   retain the marker's language identity. Review native notifications and OS
   fallback behavior on a supported emulator/device.
5. Run `npm --prefix web run i18n:generate`. The generic resource test checks Web,
   recipient and native registry parity, missing/extra semantic keys, nonempty
   copy, interpolation and locale-specific plurals. The source audit checks
   literal visible JSX/accessible text. Keep generated API code generated.
6. Review editorial/provider availability and canonical legal language separately.
   Add licensed content only through its owner and preserve explicit fallback.
7. Run resolver/resource/component and recipient tests, plus the classified
   multilingual browser journey. Shared i18n changes conservatively select the
   complete browser regression through the existing impact planner. Review
   Compact 360/390/430, Expanded, Light/Dark, 320/200% reflow, reduced motion and
   real switch-and-continue behavior. For RTL, also review logical layout/order;
   declaring `dir` alone is not visual acceptance of a new language.

## Reuse and verification

This extends the already adopted MIT-licensed i18next/react-i18next and platform
`Intl`/Android resources. FormatJS or a custom React dictionary would introduce a
second message model without an unmet requirement. No additional dependency,
external provider, content disclosure, managed translation cost or hoster setup
is needed. Resources work in Cloud/Self-Hosted and offline.

The resource/AST checks are in `web/src/i18n/i18n.test.ts`; resolver tests in
`locale.test.ts`; owned preference/focus/conflict/offline tests in
`LanguageSettings.test.tsx`; complete browser behavior in
`web/e2e/tests/multilingual-product.spec.ts`. Backend integration covers independent
Accounts, concurrency, unchanged dates/time zones and recipient dispatch; native
instrumentation covers negotiated wake validation and resource selection.
Product evidence and the implementation preflight are linked from
`docs/product/design/references/1664/README.md`.
