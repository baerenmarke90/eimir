## Current-implementation inventory (why this slice is bounded the way it is)

R2 is a rework-in-place, not a rebuild. A concrete inventory of `main` found substantially more of the R2 contract already delivered (from prior #790/#791/#860/#868/#795 work, now reinterpreted through Product Reference v1) than the issue's "likely consumers" list implies on its own:

**Already satisfies R2 today (Web):** `StoryProductPage.tsx` already has real Discover/Timeline peer tabs (`role="tablist"`), a Discover tapestry with per-kind visual roles (`media`/`note`/`milestone`/`text`, greedy-balanced columns, no masonry on mobile), a featured highlight excluded from the tapestry sequence, a year archive sourced from the server's `availableYears` (not the loaded page), and a Timeline filter sheet with **all three** `year`/`type`/`order` dimensions as a draft + explicit Apply, Cancel-discards, and visible removable chips outside the sheet. `TaskOriginProvider` already restores Timeline's mode/filters/loaded-page-count/scroll/selected-item position on Back for Memory items, with URL-based filter state (not component state) so Discover never inherits a hidden Timeline filter. `StoryYearDetailPage` already renders real semantic month headings (`<h2>`, no card wrapper) via `groupStoryItems`.

**Concrete gaps found and in scope for this slice (Web):**

1. The main Timeline tab (`StoryProductPage`, `activeView === 'timeline'`) renders one flat `StoryList` with no month grouping at all — unlike `StoryYearDetailPage`, which already has the exact required pattern. This violates reference hierarchy item 4 ("real chronological month heading — not another surrounding card").
2. `taskOriginPath()` (`taskOrigin.tsx`) only recognizes `/today`, `/story`, `/plan`, `/more` as valid return origins. `/search` is not one of them, and `SearchProductPage` never calls `captureOrigin`/passes a `taskOriginKey`. Search-origin return (acceptance journey 3) does not exist today.
3. `searchResultPath()` (`m4Product.ts`) sends `HEART_MOMENT`/`MILESTONE` search results to the bare `/story` landing page instead of their canonical `heartMomentDetailPath`/`milestoneDetailPath` — violating "a content item has exactly one canonical detail destination."
4. `HeartMomentProductPage.tsx` and `MilestoneProductPage.tsx`'s detail-mode Back link is a static `<Link to={appRoutePath('story')}>`, unlike `MemoryProductPage.tsx`, which already consumes `useTaskOrigin()`. Because `StoryList`'s `onOpenItem` already captures an origin key for *every* Story item kind (including Heart Moment/Milestone) via the same generic handler, the key is already delivered in router state today — it is just never read by these two pages. Opening a Heart Moment or Milestone from a filtered/scrolled Timeline or from Search and pressing Back currently always lands on bare unfiltered `/story`, losing scope, position and Search origin for exactly those two kinds.

**Already reasonably satisfies R2 today (Android):** `StoryScreen.kt` already composes each kind distinctly (`MemoryCard` photo-forward, `MilestoneCard` compact accent-bordered no-image, `HeartMomentCard` italic quote with optional single image) rather than one interchangeable row. `TimelineScopeControls.kt` already has a year/kind filter sheet with draft + explicit Apply, reusing `ShortTaskSheet`. `MemoryScreen.kt` is the single canonical Memory detail destination, reached identically regardless of caller.

**Concrete gaps found and in scope for this slice (Android):**

5. No Discover mode exists at all — only one Timeline stream (`StoryDestination`/`ReferenceViewModel`). This is the reference's peer-mode requirement and is explicitly called out in #966 as core R2 behavior, not deferrable to P3.
6. `TimelineScope` has `year`/`kind` but no `order` dimension, and `OkHttpReferenceApi.getScopedTimeline` does not send one. The backend endpoint (`backend/src/eimir/api/v1/story.py`) already accepts `order` (`StoryOrder`, default `DESC`) — this is a client-only gap, not a backend change.
7. Grouping is day-level only (`toStoryDays()`); there is no month heading, so "real chronological month heading" is unmet on native.
8. `TimelineScopeControls`' sheet has no explicit Cancel action (only the sheet's own dismissal), unlike Web's explicit Apply/Cancel pair.

**Explicitly out of scope for this slice (demonstrated non-defects / other owners):** Discover's Web tapestry column-balancing/weighting logic (already correct and previously reviewed under #790/#791); `aggregateStoryPages`' lack of client-side id de-duplication (the cursor contract does not produce duplicates in the append path exercised by this slice; no defect demonstrated); Android's per-kind `Surface`/card treatment (already varies meaningfully by content type; a card-removal rewrite is not demonstrated as necessary and would risk the "no gratuitous design-system rewrite" boundary); `MemoryPreview`'s single-attachment-only rendering in list contexts (`MediaGallery.tsx` already exists and is reused unchanged at the *detail* layer, which is where full gallery access belongs per the reference; list previews showing one lead image with an honest count is the specified composition, not a gap).

## Product Design Preflight and Mobile Interaction Contract

**User-facing UI/UX impact: yes.**

| Concern | Bounded contract |
| --- | --- |
| Human goal / relationship value | Recognize a shared memory by its photo or words and find an older one again without losing the browsing trail. Momente must read as rediscovering history, not administering an archive. |
| Screen Template | Story Timeline and Discovery inside Momente ([Screen Templates](../../SCREEN-TEMPLATES.md) §4/§7) for browsing; Detail View for the canonical open item; short Sheet/Dialog for the existing Filter task. |
| Primary Compact screen/state | The existing single `StoryProductPage`/`StoryDestination` surface with two peer modes (Discover/Timeline), not two separate routes — this is already the correct F2/R2-aligned boundary and is kept unchanged. |
| Dominant action | Open the chosen memory/event. Filter is the one secondary action attached to Timeline's visible scope; it does not compete with content. |
| Content hierarchy | 1) one Momente context header (unchanged), 2) Discover/Timeline peer tabs, 3) visible current scope + Filter action (Timeline only), 4) real month heading, 5) content in natural per-kind shape, 6) further month groups + pagination, 7) stable root navigation with Momente selected. |
| Immediate vs. disclosed | Applied scope, month structure and content are always visible; only the filter *sheet* itself (draft controls) is progressively disclosed behind the Filter action. |
| Interaction pattern | Existing `ShortTaskSheet`/Material `ModalBottomSheet` for Filter (reused, unchanged mechanism); full-page/full-screen detail for canonical open item; segmented tabs for Discover/Timeline. No new sheet/router/modal primitive. |

| Offline state | Existing read-cache (`productReadCache`/native M2-D18 cache banner) retained unchanged; month grouping/order/Discover peer mode operate on whatever data is present, cached or fresh. |
| Success state | Unchanged R1 contract: a confirmed create opens the actual canonical Memory. Returning from it lands on a recognizable Momente home (Timeline's restored scope, or `/story` default) even when the new Memory falls outside a previously applied filter — never fabricated as a match. |
| Privacy / relationship state | Unchanged: Story items are structurally shared-only server-side; `VisibilityBadge`/shared labelling is presentational only. No client-side privacy filtering is introduced or removed by this slice. |
| Large text / narrow viewport | 320/360/390/430 px evidenced for the new month-heading structure and the new native order control; existing D7 gutters and 44 CSS px/48 dp targets are inherited unchanged from the surfaces being extended, not re-derived. |
| Motion / reduced motion | Reuses existing `eimir-motion-reveal`/F1 tokenized transitions; no new animation. Reduced motion continues to retain all scope/focus/result information (unchanged mechanism, now also covering the added month sections and Discover tab). |

| Conventional pattern justification | A chronological vertical feed remains appropriate because reliving history in order is the actual task (Screen Templates §4); month sectioning within it is a real content grouping, not a table/list-for-its-own-sake. |

Android: existing `ShortTaskSheet`, `TimelineScopeControls`, `StoryScreen`/`StoryEntryCard`, Material `Tab`/`TabRow` for the new Discover/Timeline segmented control. |

### Concrete consumer boundaries

- **Web:** `StoryProductPage.tsx`'s Timeline branch is changed to group `combinedStory.items` via the existing `groupStoryItems` helper and render one `<section className="story-year-month">`/`<h2>` per month (reusing `StoryYearsPage.css`'s existing month-header rules verbatim, imported alongside the file's other CSS imports), with pagination's "load more" control kept once, after the last month group — not duplicated per month. `onOpenItem`/origin-capture is threaded into each month's `StoryList` call exactly as it is today into the single call. `taskOrigin.tsx` gains `/search` in `taskOriginPath`'s allowed pathname list and a new optional `searchQuery`/`searchKind` field on `TaskOriginMetadata`, mirroring the existing `loadedPageCount`/`selectedKey` pattern — no new storage mechanism. `SearchProductPage` (`M4ProductPages.tsx`) registers that metadata via the existing `registerOriginMetadata`, resolves a matching origin on mount to restore `submittedQuery`/`kind` (mirroring `StoryProductPage`'s own return-restoration effect), and its result links call `captureOrigin`/pass `taskOriginKey` exactly like `StoryList.onOpenItem` already does. `m4Product.ts`'s `searchResultPath` is changed to call `heartMomentDetailPath`/`milestoneDetailPath` (both already imported, already unused for this branch) instead of `appRoutePath('story')`. `HeartMomentProductPage.tsx` and `MilestoneProductPage.tsx` each gain the same three-line `useTaskOrigin()`/`taskState`/`returnControl` pattern already in `MemoryProductPage.tsx`, replacing only their detail-mode (not create/edit-mode) static Back `<Link>`, reusing the existing `taskBoundary.back`/`heartMomentProduct.backToStory`/`milestoneProduct.backToStory` i18n keys unchanged.
- **Android:** `TimelineScope.kt` gains an `order: StoryOrder = StoryOrder.DESC` field (new small enum reusing the existing `StoryEntryKind`-style shape, not the generated OpenAPI `StoryOrder` used server-side, to avoid a client/server model coupling this slice doesn't need). `OkHttpReferenceApi.getScopedTimeline` appends `&order=...` when non-default, matching the existing `year`/`kind` query-append pattern exactly. `TimelineScopeControls.kt` gains a third radio group (reusing the same `selectableGroup`/`RadioButton` pattern already used for kind) and an explicit Cancel `TextButton` beside Apply. `StoryEntry.kt` gains a `List<StoryDay>.toStoryMonths()`-equivalent grouping function (grouping already-produced `StoryDay`s by year-month, not re-sorting, mirroring `toStoryDays`'s own "deliberately not a sort" contract) consumed by a new small `MonthHeading` composable in `StoryScreen.kt`, inserted above each month's existing day headings — `DayHeading`, `StoryEntryCard` and the three per-kind card composables are unchanged. `ReferenceUiState` gains `storyView: StoryView = StoryView.TIMELINE` plus independent `discoverItems`/`discoverLoading`/`discoverLoaded`/`discoverHasMore` fields and private `discoverCursor`/`discoverRequestGeneration`, mirroring `refreshStory`/`loadMoreStory`'s existing structure but always requesting the unscoped `getTimeline` (no year/kind/order) — Discover's own state never touches `storyScope`/`storyItems`/`storyCursor`, so visiting Discover cannot disturb Timeline's applied filter or loaded range, and returning to Timeline needs no restoration logic because nothing was mutated. Discover renders as a single bounded (first-page, no "load more") unfiltered `StoryScreen` call with an explicit "go to Timeline" continuation action, not a new tapestry/masonry grid — this is the deliberate native-appropriate adaptation the reference allows ("platform-native interaction rather than pixel-copying Web"). `StoryDestination` (`MainActivity.kt`) gains a Material `TabRow`/`Tab` pair above the existing content, switching between the two composables; `MemoryScreen.kt`/`onOpenMemory`/System Back wiring are unchanged.

## Reuse selection (2026-09-16)

No new dependency is introduced on either platform. Web: month grouping reuses the existing `groupStoryItems`/`StoryList`/`StoryYearsPage.css` primitives verbatim — the exact pattern already proven in `StoryYearDetailPage`, just applied one route earlier. Search-origin return reuses `TaskOriginProvider`'s existing metadata-registration mechanism (already used for `loadedPageCount`) rather than inventing a second return-history system or putting the query into the URL, which would conflict with the Interaction DNA's "do not put sensitive draft/query content into URLs." Heart Moment/Milestone Back reuses the exact three-line pattern already shipped in `MemoryProductPage.tsx`. Android's order filter reuses the existing query-append idiom in `OkHttpReferenceApi`; month grouping reuses `toStoryDays`' own "group, don't sort" contract at one coarser granularity; Discover reuses `StoryScreen`, `StoryEntryCard`, `ShortTaskSheet` and the existing `refreshStory`/`loadMoreStory` structural pattern, and Material `TabRow`/`Tab` (already in the installed Compose Material 3 BOM) rather than a hand-rolled segmented control. No OSS/provider alternative was evaluated as necessary: this is a rework and light extension of already-accepted F1/F2/R1/#790/#791 primitives and the existing generated API surface, not a new capability.

## Cross-cutting review

- **Security/authorization/tenant boundaries:** unchanged — same account/Space-scoped `apis`/`ReferenceContract` calls, same generated-client authorization. Search-origin capture stores only an in-memory metadata snapshot scoped to the existing `TaskOriginProvider` account/Space generation; it never grants authorization by itself, matching F2's existing "origin does not grant authorization" rule.
- **Privacy/draft/media lifecycle:** unchanged — no new field enters logs/analytics/history/storage. The Search query text travels through `TaskOriginMetadata`'s existing in-memory-only mechanism (same 12-entry/30-minute bound as today), never through the URL, never persisted.
- **i18n/dates/long labels:** month headings reuse the existing `Intl.DateTimeFormat`/`DateTimeFormatter.ofLocalizedDate` locale-resolution paths already used by `groupStoryItems`/`DayHeading`. New native order-filter strings and an explicit Cancel string are added to the app's existing single `de` string resources, consistent with the current de-DE-only i18n surface. No new Web `de.ts` strings are needed beyond reusing `taskBoundary.back`/existing filter/search copy.
- **Accessibility/focus/scaling:** month `<h2>`/native month heading use real heading semantics (matching `StoryYearDetailPage`'s and `DayHeading`'s existing `semantics { heading() }` pattern) so screen readers get real document structure, not a second surrounding card. The native order radio group reuses the exact `Role.RadioButton`/`selectable` pattern already used for kind, so it inherits correct TalkBack behavior with no new code path. No essential control drops below 44 CSS px / 48 dp.
- **Concurrency/stale responses/duplicate submission:** unchanged for Timeline (`storyRequestGeneration`/session-guard untouched). Discover's new state uses its own independent generation counter mirroring the existing pattern exactly, so a stale Discover response cannot clear or overwrite Timeline data and vice versa.
- **Resilience/offline/retry/uncertain outcome:** unchanged — existing offline-cache/read-cache and per-region retry behavior is inherited by both the new month sections and the new Discover mode without modification.
- **Observability:** no new logging/analytics of content, search text or filter values is added.
- **Performance:** month grouping is an O(n) client-side re-pass over already-fetched items (same cost class as the existing `StoryYearDetailPage`); no new network request is added by it. Discover's own fetch is a single bounded first page, not a new unbounded cache.
- **API/DTO/compatibility/canonical routes:** unchanged — all consumed endpoints, generated types and canonical route builders (`MEMORY_DETAIL_ROUTE_PATTERN`, `heartMomentDetailPath`, `milestoneDetailPath`, native `MEMORY_ROUTE`/`HEART_MOMENT_ROUTE`/`MILESTONE_ROUTE`) are pre-existing and untouched; the native `order` query parameter is additive against an endpoint that already accepts it for Web.
- **Self-Hosted/upgrade/release impact:** none — client-only composition and wiring changes on both platforms.
- **Test levels:** unit (Vitest/RTL for the Web month-grouping/search-origin/Back changes; JVM/Robolectric for the native month/order/Discover ViewModel and Compose changes), browser (Playwright, extended for the new DOM structure and Search-return journey), and native device/emulator evidence (Robolectric renders plus, subject to device availability, on-device capture) are all planned as part of this slice; recorded under Delivery and validation below once implemented.
