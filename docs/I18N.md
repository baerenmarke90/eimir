# Internationalization and Localization

As of: 2026-08-26

## Goal

eimir. treats user-facing text, plural forms, and locale-dependent formatting as a client responsibility. German (`de`) is the default and fallback until additional language packs ship. User-generated content is never translated automatically.

## Web

Central initialization lives under `web/src/i18n/`. Language resources live under `web/src/i18n/locales/` and are addressed through stable domain-oriented keys, not through the original German source text.

Conventions:

- Keys follow the surface or domain, for example `memory.save` or `story.kind.memory`.
- German is `lng` and `fallbackLng`.
- New visible text, ARIA text, placeholders, status messages, and error messages are emitted through translation keys.
- Pluralization uses i18next suffixes such as `_one` and `_other`; feature code must not contain manual `count === 1` language logic.
- Dates and numbers use `Intl` with the active locale; feature code must not hardcode a fixed `de-DE` locale.
- A later language pack adds another resource plus `supportedLngs`; the component structure remains unchanged.

## Android

Android is the Capacitor wrapper around the Web product (ADR 0011), so it uses the
same `i18next` resources and `Intl` formatting as the Web client described above.
The native project holds only wrapper strings (`app_name`, package name); product
copy is never duplicated in `res/values/`. The former Compose client's Android
Resource/`plurals` mechanism was removed in #1009.

## API boundary

The Backend contract remains machine-readable. `ProblemDetails.code` is the stable semantic signal for clients; Backend `detail` is not a mandatory UI string. The Web reference flow preserves the error code but displays a localized client fallback. New Backend features should therefore not introduce German plaintext as a required UI contract.

## Reuse-before-build

The review under `docs/REUSE-BEFORE-BUILD.md` is relevant for this foundation.

### Options reviewed

1. **i18next + react-i18next**: established React integration, language resources, fallback, plural rules, and later runtime language switching; MIT.
2. **FormatJS / React Intl**: also an established ICU/React solution; for the current small reference client it would make the FormatJS/MessageFormat layer the primary message model even though native `Intl` already covers date and number formatting.
3. **Custom React Context/dictionary solution**: rejected. Fallback, plural rules, and language switching would be self-built commodity functionality.
4. **Android-native localization** (Android Resources, `plurals`): retired with the Compose client; Android reuses the Web resources.

### Decision

Web uses `i18next` 26.4.0 and `react-i18next` 17.0.11. Both are MIT-licensed and fit React 19 / TypeScript 5.9. They introduce no external Provider, Account, Cloud data flow, or recurring cost. Resources ship with the application and work in Self-Hosted and Cloud deployments without network access to a translation service.

The Android wrapper adds no localization dependency.

## Not part of this foundation

- no complete second language;
- no language switcher as product UX;
- no Crowdin/Weblate/Lokalise integration;
- no automatic translation of user-generated content;
- no server-loaded language packs.
