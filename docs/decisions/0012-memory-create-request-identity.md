# Decision 0012: Memory create is reconciled through a scoped request identity

**Status:** Accepted  
**Date:** September 19, 2026  
**Owning issue:** #961  
**Builds on:** F2 task boundaries (#958) and the commit-before-success rule from #243

## Context

`POST /spaces/{spaceId}/memories` commits in the request unit of work before the response is exposed. The
commit can therefore succeed while the caller loses the response (network drop, client timeout, tab
suspension). The client then knows neither whether the Memory exists, nor its canonical ID, nor whether a
second POST would create a duplicate. F2 (#958) deliberately stops at an honest "unknown outcome" state and
forbids a blind repeat; a disabled button, a session flag or a title/date search cannot close the gap
because none of them is anchored in the server's transaction.

## Reuse review (`docs/REUSE-BEFORE-BUILD.md`)

| Candidate | Finding |
| --- | --- |
| IETF `Idempotency-Key` HTTP header field (`draft-ietf-httpapi-idempotency-key-header`) | Open, widely deployed convention for exactly this problem (retry-safe `POST`). Not yet an RFC, so this decision adopts the header name and the "same key, different payload is an error" rule without claiming conformance. No library is needed. |
| PostgreSQL unique index + `INSERT ... ON CONFLICT DO NOTHING` | The transactional primitive that makes "key claimed" and "Memory created" one atomic step and serializes simultaneous requests. Already the repository's concurrency substrate. |
| In-repo `ThinkingOfYouRequest` (`client_request_id`, unique per Space + sender) | Same shape (client-supplied UUID, unique per Space and Account), but it is a cooldown receipt with no payload check, no stored resource reference, and no lifetime. Its idea is reused; its table is not, because a stored `memory_id` with a foreign key is Memory specific. |
| In-repo 200/201 replay precedent (`convertWishToPlan`) | Reused: first call `201`, equivalent replay `200` with the same body shape. |
| In-repo TTL prune pattern (`discover_selection_snapshots`, story view aggregates) | Reused: retention constant + prune function run by the existing `security_retention` job; no new scheduler. |
| Framework/library idempotency middleware (Stripe-style response caching) | Rejected: caches whole responses (would store Memory content) and is not transactionally tied to the create. |
| Operation-result lookup (`GET .../memory-create-results/{id}`) | Rejected, see below. |

## Decision

`POST /spaces/{spaceId}/memories` accepts an **optional** `Idempotency-Key` request header.

- **Value:** a UUID in canonical text form, generated by the client per user-initiated save. Anything else is
  `422 IDEMPOTENCY_KEY_MALFORMED`. Without the header the operation behaves exactly as before (older clients
  stay valid; no receipt is written).
- **Scope:** the tuple *(Space, authenticated Account, key)*. The operation is implicit (the table only
  serves Memory create). The key never grants anything: Space membership and Account authentication are
  resolved first by the normal dependencies. The same key used by another Account or in another Space is
  simply an unrelated, unseen key, so no cross-tenant probing is possible and nothing is revealed.
- **Stored metadata (`memory_create_receipts`):** key, Space ID, Account ID, a SHA-256 fingerprint of the
  normalized request (`title`, `body`, `happenedOn`), the created Memory ID and the creation time. The request
  body itself is never stored.
- **Atomicity:** the receipt is claimed with `INSERT ... ON CONFLICT (space_id, account_id, key) DO NOTHING`
  in the same transaction as the Memory and its outbox event. A rollback discards both. Two simultaneous
  equivalent requests serialize on the unique index: the second waits for the first to commit, then observes
  the receipt and replays; if the first rolls back, the second proceeds to create.
- **Replay (same identity, same fingerprint):** `200 OK` with the *current* representation of the original
  Memory (it may already carry attachments or edits) and its current `ETag`. Nothing is written.
- **Identity reuse with a different payload:** `409 Conflict`, code `IDEMPOTENCY_KEY_REUSED`. Neither payload
  wins silently. (The IETF draft proposes `422` here and `409` for a concurrent in-flight request; because
  this design serializes on the database and never reports "in flight", `409` is free and matches the
  repository's conflict convention and the issue text.)
- **Original Memory deleted later:** the foreign key is `ON DELETE SET NULL`, so the receipt survives and the
  replay answers `404 MEMORY_CREATE_RESULT_DELETED`. The Memory is never resurrected by a stale retry, and
  only the authoring Account within its own Space can ever see this answer.
- **Unknown or expired key:** indistinguishable from a first use and creates normally. Only a key that is
  older than the retention window can therefore duplicate, which is why clients must stop replaying a key
  after a safe margin (below).
- **Lifetime:** `RECEIPT_RETENTION = 24 hours` from creation, pruned by the existing `security_retention`
  maintenance job (an indexed `created_at` range delete). Cloud and Self-Hosted use the same code path and the
  same constant. Rows also cascade with their Space and Account and are removed explicitly on membership end
  (`end_membership`) and Account deletion core cleanup, because pseudonymized Accounts are not hard-deleted.
- **Migration:** additive table, no backfill, no change to existing rows. Rollback drops the table; a replay
  after a rollback of the deployment simply becomes a first use.
- **Cost:** one row of roughly 150 bytes plus two index entries per identified save for at most 24 hours.
  No new quota, entitlement or provider.
- **Diagnostics:** the fingerprint, key and payload are not logged. Only counts are logged by the prune job.

### Client recovery contract

1. The client generates one key when a save starts and keeps it, in memory, together with the exact submitted
   snapshot for as long as the outcome is unknown.
2. If the outcome is unknown (transport failure, timeout, `5xx`), the client keeps the input and tells the user
   that it is verifying whether the entry was saved. It never sends a *new* key for the same draft.
3. Verifying means re-sending the identical request with the same key (user-initiated, no timers). `200` or
   `201` yields the canonical Memory ID; the client opens exactly that Memory and continues with the existing
   attachment binding for that ID. A definitive `4xx` is shown honestly.
4. Clients stop replaying a key after **12 hours**, half the server retention, to absorb clock skew, and
   then state that the entry can no longer be verified and that the user should check the Moments list before
   creating it again.

## Alternatives rejected

**Narrowly authorized operation-result lookup** (a `GET` that returns the Memory ID for a client-supplied
request ID). It needs the same stored identity, the same lifetime and the same authorization as the header
approach, plus a second endpoint and a client that must choose between "lookup" and "create". It also cannot
close the race that matters: while the original request is still executing on the server, a lookup reports
"not found" and a subsequent create with a fresh identity would duplicate. Replaying the *same* identity
against `POST` blocks on the database and cannot. The header contract subsumes the lookup and is the smaller,
safer contract.

**Column on `memories`.** Cheaper, but the identity disappears with the Memory, so a stale retry after a
deletion (for example from another device) would resurrect deleted content, and the identity would live as
long as the Memory rather than a bounded time.

**Title/date search, client-only flags, disabled buttons, automatic timed retries.** None is anchored in the
server transaction.

**Generic idempotency framework / all-domain retrofit.** Out of scope; other create endpoints keep their
current semantics. If another domain needs the same guarantee, extracting the tiny header parser and
fingerprint helper is straightforward.

## Attachment boundary

Memory create and attachment binding stay separate steps. Attachment upload drafts remain owned by the
uploading Account and Space; binding still uses `PUT .../attachments` with `If-Match` against the Memory ID.
Recovery therefore never answers "Memory ID unknown" with another create: the client first reconciles the
original Memory through the replay, then continues the existing binding path against that canonical ID.

## Business/freemium consistency

No business/freemium impact. Memory CRUD/Timeline and reliable recovery remain Free/Core and non-paywallable
(`docs/FREEMIUM-FEATURE-MATRIX.md`). Cloud and Self-Hosted get identical behavior; the retained metadata is
bounded and negligible, with no new quota, storage tier or downgrade semantics.

## Consequences

- Older clients keep working unchanged and remain subject to the F2 "unknown outcome" limitation.
- The generated TypeScript client gains an optional `idempotencyKey` parameter and an explicit `200` response,
  `409`/`404` codes and a `422` code on `createMemory`.
- Follow-ups for other create endpoints must make their own scoped decision; this one is not a platform.
